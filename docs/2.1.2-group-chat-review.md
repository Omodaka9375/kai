# Group chat feature audit (2.1.2)

Date: 2026-11-01. Four parallel audit passes: trust boundary (security), state
machine (correctness), panel (React/UI), integration seams. All findings below
were re-verified at the source after the audit passes returned them.

## Verdict

The fence-laundering trust boundary holds on every enumerated path: no
exploitable route was found for one participant's output to reach another
model's context as trusted content. The prior aa9572e fixes all still hold.
However, three MUST-class correctness defects were confirmed (persona approval
leaks on teardown, headless personas can mutate the global agent registry and
schedule persistent reminders with no approval, single-session machinery breaks
when one project joins two groups). These are behavior bugs, not security
breaks.

## What holds (re-verified)

- Coordinator wake text is fenced at buffer push (noteParticipantReply
  groupChatStore.ts:1856, the only `.replies.push` in the codebase); both
  flush builders in flushCoalesced build from pre-fenced entries.
- send_to_project and @-mention deliveries fence agent-authored text with the
  TARGET session's own nonce (deliverToParticipant, transport.ts fenceGroupText
  reads the same fenceStateCache the target's run reads).
- Persona deliveries use the cached per persona+group fence state; the nonce
  taught in the persona system prompt is the nonce used at delivery.
- User sends stay unfenced by design; no agent-authored group text enters any
  system prompt (the coordinator preamble is a user message).
- Fence-marker forgery is neutralized even with nonce knowledge: fence()
  runs neutralizeFenceMarkers matching ANY `[start|end (tool|web|watch|mcp)_...]`
  regardless of nonce, with a visible `[kai: ...]` notice.
- Approvals resolve only through the latched responders; no path parses
  message text as an approval decision. Deny latching is monotonic everywhere.
- send_to_project is hard-bound to the coordinator's own roster; unknown
  targets and self-sends are rejected; the tool requires approval.
- @coordinator alias resolves before the name matcher, agent-kind only, never
  self-routable; a participant named "coordinator" cannot shadow it.
- TTS: no group path reaches speakText; the three injection markers and the
  bridge's wasGroupRef snapshot are in lockstep (pinned by ttsCausality.test).
- Timer/queue hygiene on end/reclaim/remove is correct
  (teardownSessionMachinery); LRU eviction of live participants is blocked by
  the pinner; injectMessage rehydrates persisted history for evicted chats.

## MUST findings (verified)

### M1. Persona approval cards leak on group end/delete/remove

`teardownSessionMachinery` (groupChatStore.ts:1943) sweeps personaQueues,
personaAborters, personaBusy but never touches `personaApprovals`.
`denyPersonaApprovals` is called only from `abortPersonaMachinery` (the human
Stop paths) and from the in-run dead-group check at :1011. That check sits at
the top of the round loop, BEFORE `await Promise.all(decisionPromises)`
(:1090). When a persona is parked at the await and the group is ended, deleted,
or the participant removed:

- The abort signal does nothing (generateText already returned for this round).
- Nothing resolves the decision promises: the run leaks (hung async state).
- The registry entry stays in `personaApprovals` forever: GroupPill shows a
  phantom pending-approval badge with no group to answer it.
- A later Approve click resumes a run for a dead group (it throws on the
  aborted signal only by accident of the aborter surviving teardown).

The code comment at :1007 claims "denyPersonaApprovals already did on
teardown" - false.

Fix: in teardownSessionMachinery, sweep personaApprovals by the same
`::${sessionId}` suffix rule used for personaQueues: delete the entry and call
`entry.decide(false)`.

### M2. Headless personas can mutate global user surfaces with no approval

The persona toolset filter (groupChatStore.ts:866-880) removes only
PERSONA_EXCLUDED_TOOLS + send_to_project + project_status. PERSONA_EXCLUDED_TOOLS
(personaWorkspace.ts:130) does NOT exclude:

- `create_persona` / `set_persona` (persona.ts:67, needsApproval: false): a
  headless group participant can permanently mutate the user's global agent
  registry (useAgentsStore.upsert) and persist a session preference under its
  synthetic id. Same class as `settings`, which the list already excludes with
  the comment "a headless group participant has no business re-configuring
  the app".
- `reminder_create` / `reminder_list` / `reminder_cancel` (reminders.ts, all
  needsApproval: false): a headless participant can schedule persistent
  notifications that survive restarts and ping the owner's Telegram.
- `mcp_add_server`: approval-gated, but it mutates global MCP config from a
  headless context (defense-in-depth exclusion candidate).

Fix: add create_persona, set_persona, reminder_create, reminder_list,
reminder_cancel (and mcp_add_server, invite_agent as defense-in-depth) to
PERSONA_EXCLUDED_TOOLS.

### M3. One project in two groups cross-routes all session-keyed machinery

`sessionGroups`, `awaitingReply`, `sendQueues`, `pendingReplies`, and
`coalesceTimers` are keyed by sessionId with no groupId dimension, and
nothing in createGroupChat/addParticipants prevents dual membership:

- A participant in groups A and B gets deliveries from both merged into ONE
  injected message; its single reply mirrors into whichever group armed the
  reply provision last; the other group times out with "no reply".
- `coordinatorGroupForSession` (:374) returns the FIRST live group; a project's
  agent delegated as coordinator in groups A and B is dead in B: no preamble,
  no group tools, send_to_project reaches only A.
- `pendingReplies[coordSession]` is shared across both groups: replies from
  A's and B's participants merge into one mixed wake with no group named.
- `delegateCoordination` never tears down the OLD coordinator's armed
  coalesce buffer/timer: after re-delegation the timer fires a spurious wake
  into a now-plain participant, burning a model run on chatter addressed to
  the new coordinator.

Fix options: key the maps by `groupId::sessionId` and the buffers by
`groupId::coordinatorSessionId`; refuse dual membership while the session is a
live member of another group; tear down old-coordinator machinery in
delegateCoordination.

## SHOULD findings

1. `session:delete` on a persona id (groupChatStore.ts:2027-2056) removes the
   participant but never aborts its in-flight run; the finished reply lands
   via appendGroupMessage (no membership check) and its @-mentions still route.
2. hydrateGroups rehydrates groups whose participant projects were not
   restored. Sends fall back to the stale persisted sessionId, injectMessage
   fabricates a chat no bridge watches, and the reply never mirrors while the
   panel shows "delivered". Prune dead participants at hydrate.
3. hydrateGroups has no per-record guard: one malformed record (missing
   participants) throws mid-loop, leaving partial state and a cached rejected
   hydratePromise for the whole app lifetime.
4. Coordinator preamble re-injects on every boot (preambleGivenRef is a React
   ref): a live coordinator group whose session survived a restart gets an
   unrequested model run at startup.
5. appendGroupMessage persists EVERY group's ENTIRE transcript on every
   message; transcripts are never trimmed. A long-lived group makes each send
   O(total history). Full-file rewrite on every message, no corruption
   recovery, no schema version.
6. Transcript auto-scroll (GroupChatPanelView.tsx:643) force-scrolls on
   `from === "agent"` too, contradicting its own comment: an agent reply
   yanks the user out of a manual scroll-up.
7. Transcript renders the full persisted history with per-bubble markdown
   parsing on every version bump (version fires on status changes too). Window
   the list or memo GroupMessageBody.
8. Composer send has no catch (GroupChatPanelView.tsx:1178): a delivery
   rejection is an unhandled promise, silently never sends.
9. The tray's end-then-delete chain (GroupChatPanelView.tsx:270) has no
   rejection path: if endGroupChat rejects, the group stays live with no
   feedback. Same void-async-without-catch class at ~7 more call sites.
10. Fence nonces derive from Math.random via the SDK's generateId (~47.6 bits,
    per-session, never rotated). Neutralization makes nonce knowledge
    non-exploitable today; crypto.getRandomValues would be defense-in-depth.
11. The coordinator's sessionId is never re-resolved on later access the way
    participant sessions are; delegation silently rots if the coordinator
    project switches chats.

## NITs

- personaFenceStates and mentionChain entries leak on deleteGroupChat (swept
  only by the test reset); slow unbounded growth.
- participantActivity matches approvals by sessionKey suffix, so a persona
  awaiting approval in group A shows "approval" in group B's strip too.
- GroupPill's badge counts only persona approvals; a background participant
  session awaiting approval does not count (tooltip under-promises).
- invite_agent's announce text is agent-authored but labeled from: "system"
  in the transcript (inert today: the only model-facing consumer re-fences
  the whole snippet).
- matchParticipantByToken uses substring includes: a short @token can
  misroute to the wrong member (routing only; all targets get fenced text).
- With a user-coordinator, @coordinator falls through to the name matcher and
  can substring-match an unrelated participant.
- Rename input lacks maxLength=120 (store caps silently at commit).
- pickMention calls setText/queueMicrotask inside the setMention updater
  (impure updater; idempotent today).
- Persona edit approvals have no diff view anywhere (card shows the summary
  only).
- A user-pasted transcript line containing " cross-project group] "
  false-positives the TTS group marker.

## Recommended order

M1 and M2 are small, contained fixes (one sweep loop; one list). Ship them
first. M3 is a design-level change (keying or membership refusal) - decide the
approach before touching it. SHOULDs 1-3 are next (lifecycle/robustness),
then the UI rejection paths (8-9), then perf (5-7).
