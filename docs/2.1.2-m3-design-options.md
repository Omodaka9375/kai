# M3 design options: one project in multiple groups

Decision doc for audit finding M3 (docs/2.1.2-group-chat-review.md). Nothing
in the group machinery has a groupId dimension on its session-keyed state, so
one project joining two live groups cross-routes deliveries. This doc lays out
the fix options and what each costs. No code changed yet.

## Why it breaks

Two seams make dual membership structurally broken today, not just buggy:

1. The reply mirror is single-answer. The bridge (AgentRunBridge.tsx:541)
   asks `peekReplyProvision(sessionId)` / `takeReplyProvision(sessionId)`
   when a run finishes. One session, one armed provision slot
   (`awaitingReply: Map<sessionId, groupId>`, groupChatStore.ts:395). A
   session armed by groups A and B can answer only one; `armReplyProvision`
   overwrites (:1183), so whichever group armed last wins and the other
   group's coalesce timer times out with "no reply". The bridge cannot
   disambiguate either: one finished assistant run is one text object.

2. The coordinator binding is first-match. `coordinatorGroupForSession`
   (:373) scans live groups in map order and returns the first whose
   coordinator session matches. `buildGroupTools` (tools/group.ts:48) binds
   `send_to_project` and `project_status` to exactly that group, and the
   bridge's preamble gate keys on it (AgentRunBridge.tsx:373). An agent
   coordinating groups A and B is dead in B: no preamble, no group tools,
   and its `pendingReplies` buffer (keyed by coordinator session, :147)
   merges replies from both groups into one mixed wake text.

Supporting facts (verified):

- Membership is PROJECT-scoped in practice. Invitee sessions resolve from
  `getProjectActiveSession(projectId)` at creation (:513), and every send
  path re-resolves the project's current active session. A second chat in
  the same project does not give you a second addressable member.
- `delegateCoordination` picks coordinators from the group's own
  participants (:1680), so every agent-coordinator is also a participant. A
  participant-project-scoped invariant therefore covers coordinators too.
- Personas are ALREADY multi-group-safe: their machinery is composite-keyed
  (`groupId::sessionId`, :196), they have no bridge, no sendQueues entry,
  and hydrate deliberately skips them in the sessionGroups index (:446).
  Any fix must NOT block persona dual membership.
- `groupsForProject(projectId)` (:425) already answers "is this project in
  a live group" for participants.

## Machinery inventory

Session-keyed (the problem):

| Map | Key | Breaks dual because |
|---|---|---|
| `sessionGroups` :390 | sessionId -> groupId | last writer wins; bridge mirror lookup |
| `awaitingReply` :395 | sessionId -> groupId | one reply provision per session |
| `sendQueues` :388 | sessionId -> msgs[] | flush merges all groups' texts into one inject (:1148) and arms only the last group's provision |
| `pendingReplies` :147 | coord sessionId | one coalesce buffer merges replies from every group the session coordinates |
| `coalesceTimers` :148 | sessionId | one timer per session |
| `relayDepth` :118 | coord sessionId | hop counter shared across groups |

Already group-aware (fine): `mentionChain` (groupId), personaQueues /
personaAborters / personaBusy / personaApprovals / personaFenceStates
(groupId::sessionId or persona key).

Independent bug under every option: `delegateCoordination` (:1672) never
tears down the OLD coordinator's armed buffer/timer, so a re-delegated
coordinator can fire a spurious wake into a now-plain participant.
`reclaimCoordination` (:1700) does tear down. This should be fixed
regardless of the option chosen.

## Option A: enforce single membership (project granularity)

Make "one project in one live group at a time" a store invariant, enforced
at the entry points, and keep all session-keyed maps exactly as they are.
The invariant makes them correct by construction.

Invariant: for any two live groups, no projectId appears in both
participants lists (agent-coordinators are participants, so they are
covered). Personas exempt (composite machinery, no bridge).

Enforcement points:

1. `createGroupChat`: refuse when the inviter or any invitee project is a
   live member elsewhere. Return value needs a reason; today it returns
   `GroupChat | null` (null only for empty invitees).
2. `addParticipants`: same check per new invitee.
3. `addPersonaParticipants`: NOT blocked (personas may be in many groups).
4. `delegateCoordination`: the delegate is a member of THIS group already,
   so under the invariant it cannot be live elsewhere. No extra check
   needed once 1 and 2 hold.
5. `resumeGroupChat`: an ended group resuming must re-check all members
   against other live groups; conflicted members drop with a system note.
6. `hydrateGroups`: persisted state may predate the rule. Prune
   deterministically: earlier group (lower createdAt) wins; conflicted
   members of later groups drop with a system note at hydrate.

UX: the InvitePicker disables conflicted projects with the owning group's
name in the row (prevention), and the store refusal is defense in depth
(same pattern as the persona-delegation guard). The GroupListTray "new
group" entry shows why a project cannot join.

Cost: small. One predicate (`projectInLiveGroup(projectId)`), five call
sites, picker UI states, plus the delegateCoordination teardown fix.

Benefit: M3-class cross-routing becomes structurally impossible, including
for future code that adds a new map keyed by session. The session-keyed
design stays simple and debuggable.

Risk: the invariant is only as good as its enforcement. A behavioral test
per entry point plus a source pin on the picker keeps it honest. Sequential
membership still works (end group A, join group B), which is the common
case.

What it costs users: a project genuinely cannot sit in two rooms at once.
Given membership is project-scoped anyway (the active session IS the
member), a second room would receive the same agent's attention with one
context; the practical value is low.

## Option B: re-key all machinery by group and session

Keep dual membership legal and make it work.

Shape: move per-group runtime state INTO each GroupChat record instead of
module maps. Each group holds its own `sendQueues`, `pendingReplies`,
`coalesceTimer`, `relayDepth`, and an `awaitingReply` set (strip runtime
fields on persist). Session-keyed lookups become scans over live groups,
like `coordinatorGroupForSession` already is. Composite maps like
personaApprovals become per-group state too, which also removes the string
suffix sweeps M1 added.

The two hard seams then need real design work:

1. Reply mirroring. `takeReplyProvision` must return every armed group.
   Two sub-shapes:
   - B1: fan-out. One assistant reply mirrors into EVERY group that had a
     provision armed. Simple, but both coordinators receive text answering
     a merged context, and mention routing fires per group.
   - B2: tag-and-route. Deliveries carry a machine-readable group tag the
     bridge echoes back, so the reply routes to the group that provoked
     it. This changes the injected text format (`[name - cross-project
     group]` marker), which is pinned by TTS-exclusion tests and
     isGroupDeliveryText consumers.
2. Coordinator tools. `send_to_project` gains a groupId parameter (or the
     roster text must list groups and the tool validates against the named
     group's roster). Schema change rippling into toolPresentations, the
     preamble text, and the drift-gated KAI.md inventory.
3. The preamble gate (`preambleGivenRef`) must become per group per
   bridge.

Cost: large. Touches the bridge seam, the tool schema, transport marker
contracts, the fence-laundering tests, TTS pins, the M1 teardown test, and
every source pin that references the current message shapes. Realistically
several days plus a full audit re-run of the trust boundary, since the wake
and mention paths change shape.

Benefit: the feature works. Dual membership becomes a real capability.

Risk: the reply-ambiguity problem does not fully disappear. One assistant
run still answers ONE merged context when two groups delivered back to
back; B2 routes the text but cannot split the model's attention. The
feature's value is bounded by that.

## Option C: coordinator-only enforcement (rejected)

Enforce the invariant only for agent-coordinators (the worst cross-routing)
and leave participant dual membership possible. Rejected: participant
cross-routing (merged queue flush, lost mirror) is exactly the reported
failure mode, and a half-invariant invites the same drift it tries to
prevent.

## Recommendation

Option A, plus the independent delegateCoordination teardown fix. Reasons:

- The broken scenario is rare (dual membership is not currently advertised
  anywhere; nothing in the panel suggests it is supported).
- The cost asymmetry is extreme: A is a day, B is a multi-day re-architecture
  plus a security re-audit of changed paths.
- A makes a future B cheaper, not harder: an enforced single-membership
  baseline is the safest place to migrate from if dual rooms ever become a
  real feature request.

## Sub-decisions needed if A is picked

1. Refusal surface: createGroupChat currently returns null on empty
   invitees. Proposal: add a reason return (discriminated union or a
   `lastRefusalReason` accessor) so the picker can show it; picker rows are
   disabled pre-emptively anyway.
2. Hydrate conflict policy for a COORDINATOR clash (later group's agent
   coordinator is live in an earlier group): proposed default is to drop
   the conflicted member with a note and fall that group back to a
   user-coordinator (kind "user" is a legal, documented state with no
   coalescing). Alternative: end the later group at hydrate with a note.
3. Resume policy: drop conflicted members with notes (proposed), or refuse
   the resume outright while any member is conflicted.

## Test plan sketch (A)

- Behavioral: create with conflicted invitee refuses; addParticipants
  conflicted refuses; personas unaffected; resume drops conflicted member
  with note; hydrate prunes later group deterministically; delegate leaves
  no armed timer on the old coordinator (the teardown fix).
- Source pin: picker disables conflicted rows with the owning group name.
